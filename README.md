# 1c-ai-data-guard

[English version](README.en.md)

Комплект, который позволяет работать с базами 1С вместе с ИИ-агентами и не отдавать им реальные персональные данные.
Два профиля: **Казахстан** (ИИН/БИН, IBAN KZ, БИК, номера `+7`) и **Россия** (ИНН, КПП, ОГРН, СНИЛС, расчетные счета).

Главная идея: надежно не то, что данные замаскированы, а то, что реальных данных у модели нет. Поэтому два уровня.

| Уровень | Что делает | Статус |
|---|---|---|
| 1. Обезличенная копия | Обработка 1С заменяет персональные данные в копии базы синтетическими, с верными контрольными цифрами. Агент работает с копией | работает: профиль KZ проверен на копии Бухгалтерии для Казахстана, профиль RU на копии Бухгалтерии предприятия |
| 2. Шлюз для живых данных | Прокси между ИИ и OData 1С: белый список объектов и полей, подмена значений токенами, запрет фильтров по реальным значениям | готов (`gateway/`), проверен на поддельном источнике и на живом OData 1С (Бухгалтерия для Казахстана через IIS) |
| 3. Проверка утечки | «Канарейки»: заведомо известные значения кладутся в источник, набор атак на шлюз (26 на живом OData), проверка, что ни одно не вышло открытым текстом | готова (`canary/`) |
| Ядро | Проверка и генерация идентификаторов, поиск и подмена в тексте | готово, `dataguard/` |

## Быстрый старт

Нужны: Windows, платформа 1С 8.3 (проверено на 8.3.27), Python 3.10+ без дополнительных пакетов, PowerShell.

### Сценарий 1. Обезличенная копия базы для разработки и тестов

Для программиста или ИИ-агента, которому нужна база «как настоящая», но без настоящих людей.

1. **Сделайте копию файловой базы** в папку, в пути которой есть `_test` (например, `D:\Bases\buh_test`). Без `_test` в пути обработка
   ничего не заменит. Рабочую базу не трогайте. Журнал регистрации в копию не переносите.
2. **Соберите обработку** из исходников `1c/src` в `1c/build/ОбезличиваниеДанных.epf` (подойдет любая файловая база, хоть пустая):
   ```
   1cv8.exe DESIGNER /F"<любая база>" /DisableStartupDialogs /LoadExternalDataProcessorOrReportFromFiles "1c\src\ОбезличиваниеДанных.xml" "1c\build\ОбезличиваниеДанных.epf"
   ```
3. **Посмотрите, что есть в базе** (только чтение, реальные значения в отчет не попадают):
   ```
   .\1c\run.ps1 -BasePath D:\Bases\buh_test -User Админ -Profile KZ -Mode ИНВЕНТАРИЗАЦИЯ -Report inventory.txt
   ```
   Профиль `KZ` - Бухгалтерия для Казахстана, `RU` - Бухгалтерия предприятия. Если в отчете есть реквизиты, которых нет в
   `1c/rules/<профиль>.txt` (доработки, свои справочники), допишите их в копию файла правил.
4. **Обезличьте копию.** Секрет - любая строка от 16 знаков, сохраните его, пока проверяете результат. Снимок - файл хешей исходных
   значений для проверки, реальных значений в нем нет.
   ```
   .\1c\run.ps1 -BasePath D:\Bases\buh_test -User Админ -Profile KZ -Mode ВЫПОЛНЕНИЕ -ConfirmTestCopy `
       -Rules 1c\rules\kz.txt -Secret "<секрет>" -Snapshot snapshot.txt -Report run.txt -TimeoutSec 7200
   ```
5. **Проверьте результат**: ни одного исходного значения, верные контрольные цифры, обезличенные пользователи.
   ```
   .\1c\run.ps1 -BasePath D:\Bases\buh_test -User Админ -Profile KZ -Mode ПРОВЕРКА -Rules 1c\rules\kz.txt -Snapshot snapshot.txt -Report check.txt
   .\1c\run.ps1 -BasePath D:\Bases\buh_test -User Админ -Profile KZ -Mode ОСТАТКИ -Report rest.txt
   ```
   После этого копию можно отдавать ИИ-агенту или разработчику. Снимок и секрет удалите.

Другая версия платформы - параметр `-Platform "C:\Program Files\1cv8\<версия>\bin\1cv8.exe"`.
Если платформа спрашивает «Разрешить открывать данный файл?», выполните один раз режим `ЗАЩИТА` (только на копии).

### Сценарий 2. ИИ читает живую базу через шлюз

Для бухгалтера, аналитика, руководителя: вопросы ИИ по данным рабочей базы, а ИИН, имена и счета до модели не доходят.

1. **Опубликуйте OData базы** на веб-сервере (IIS или Apache) и включите в «Составе стандартного интерфейса OData» нужные справочники,
   документы и регистры. Заведите для шлюза отдельного пользователя 1С с правами только на чтение.
2. **Опишите политику**: какие наборы и поля видит ИИ. Начните с `gateway/examples/kz.policy.json` или `ru.policy.json`, в
   `upstream.base_url` укажите адрес публикации. Поля с персональными данными - `token:<класс>`, прочие - `pass`. Чего нет в политике,
   того ИИ не увидит.
3. **Запустите шлюз** под отдельной учетной записью Windows (секрет и пароль 1С не должны быть доступны ИИ):
   ```
   set DATAGUARD_SECRET=<не короче 16 знаков>
   set ODATA_USER=<пользователь 1С> & set ODATA_PASSWORD=<пароль>
   set DATAGUARD_CLIENT_TOKEN=<необязательный ключ клиента>
   py -m gateway.server --policy my.policy.json --port 8790
   ```
4. **Проверьте шлюз до подключения ИИ**: `py -m canary --selftest`, затем на живой базе - канарейки (раздел «Проверка утечки» ниже).
5. **Подключите ИИ-клиент**: в любом OData MCP-сервере или своем скрипте укажите адрес шлюза `http://127.0.0.1:8790` вместо адреса 1С
   (наборы запрашиваются как `http://127.0.0.1:8790/Catalog_Контрагенты?$top=10`), заголовок `X-Gate-Token`, если задан ключ клиента.

## Ядро (`dataguard/`)

Стандартная библиотека Python, без зависимостей.

- `checksums.py` - ИИН, БИН, IBAN, ИНН, СНИЛС, ОГРН: проверка и генерация. Проверено по публичным примерам (IBAN из реестра ISO, ИНН и ОГРН крупных банков, пример СНИЛС из описания алгоритма).
- `scanner.py` - поиск по профилю (`profile_kz()`, `profile_ru()`), детерминированные токены `[[iin:M4T2Q9XZ7K]]` (HMAC-SHA256 с секретом шлюза), словарь известных значений для ФИО и названий в свободном тексте, `leak_check` для проверки утечки.

```
py -m unittest discover -s tests
```

## Шлюз к OData (`gateway/`)

Прокси между ИИ-клиентом (любой OData MCP) и OData 1С. Клиент ходит на адрес шлюза, а не 1С; адрес и учетные данные 1С знает только шлюз
(переменные окружения), редиректы запрещены.

```
set DATAGUARD_SECRET=<не короче 16 знаков>
set ODATA_USER=... & set ODATA_PASSWORD=...
py -m gateway.server --policy gateway\examples\kz.policy.json --port 8790
```

- **Только чтение.** `GET` и `HEAD`, остальное - 405. Разрешены параметры `$select`, `$filter`, `$top`, `$skip`, `$orderby`, `$count`, `$format=json`; `$expand`, `$metadata`, `$batch` недоступны.
- **Белый список.** В политике (`*.policy.json`) перечислены наборы данных и поля. Поля вне политики наружу не выходят и в `$select` недоступны. Режим поля: `pass` (отдается как есть, но строки проходят «стража»: шаблоны ИИН/БИН, IBAN, телефона, e-mail заменяются токенами) или `token:<класс>` (значение заменяется токеном `[[класс:XXXXXXXXXX]]`, HMAC с секретом шлюза).
- **Фильтры не открывают значения.** По защищаемому полю искать можно только токеном из ответа шлюза (шлюз подставляет настоящее значение при запросе к 1С), сравнение только `eq` и `ne`. Реальный ИИН, имя, подстрока, `or`, функции, сортировка по защищаемому полю отклоняются. Это закрывает перебор: по неизвестному токену ничего не находится.
- **Ограничения и ошибки.** `$top` обрезается политикой; тексты ошибок источника не передаются (общее сообщение со статусом); журнал шлюза содержит метод, набор, статус и число строк, но не значения.
- Необязательный заголовок `X-Gate-Token` (`DATAGUARD_CLIENT_TOKEN`): чужой процесс на машине без него шлюзом не пользуется.

Секрет токенов и учетные данные 1С не должны быть доступны сессии ИИ: запускайте шлюз под отдельной учетной записью ОС.

## Проверка утечки (`canary/`)

```
py -m canary --selftest                       :: без 1С: шлюз над поддельным источником
py -m canary --gateway http://127.0.0.1:8790 --canaries canaries.json   :: живой шлюз
```

`make_canaries()` создает выдуманные, но правдоподобные данные (ИИН/ИНН с верными контрольными цифрами, телефоны, e-mail, счета, имена,
паспорт, текст с ними вперемешку). Набор атак (`canary/battery.py`) пробует реальный ИИН и имя в фильтре, подстроки, `or`, сортировку,
`$expand`, метаданные, пакетные запросы, запись, выход из пути, эхо ошибки источника, ИИН внутри поля `pass`. После прогона каждая
канарейка ищется в ответах и журнале шлюза в любых форматах (с пробелами, дефисами). Тесты в `tests/test_gateway.py` проверяют и защиту,
и чувствительность детектора: заведомо слабая политика (имена как `pass`, паспорт как `pass`) обязана давать утечки.

**Живая проверка (OData Бухгалтерии для Казахстана через IIS).** Обработка включила стандартный интерфейс OData для справочников
(режим `ОДАТА`), посадила восемь канареек с кодами `CANDG0001…` прямо в базу контрагентов (режим `КАНАРЕЙКИ`, потом `УДАЛИТЬКАНАРЕЙКИ`),
база была опубликована в IIS, шлюз стоял над ней. Основной шлюз (комментарий вне политики): через него получены все 8 канареек
(имя и ИИН - токены), 26 атак, утечек 0. Контрольный опыт со слабой политикой (комментарий как `pass`) дал 9 утечек имен: ИИН, телефон
и e-mail из того же комментария страж заменил токенами, а имя без шаблона пропустил. Важно для проверки: канарейки должны быть в
ответах шлюза (поэтому они получают отличимый код и достаются по нему), иначе «0 утечек» ничего не доказывает.

Что это доказывает и что нет: шлюз не отдает канарейки из полей вне политики и не позволяет их угадывать фильтрами. Это не доказывает,
что в разрешенных полях нет персональных данных, которых нет в списке шаблонов (поэтому для имен, названий и текстов нужен режим
`token:*`, а не `pass`). Самопроверка на поддельном источнике не заменяет прогон на живом OData вашей базы с вашей политикой.

## Обработка обезличивания (`1c/`)

Внешняя обработка 1С, запускается из командной строки на копии файловой базы: `1c/run.ps1`. Режимы:

| Режим | Что делает |
|---|---|
| `ИНВЕНТАРИЗАЦИЯ` | Только чтение: какие чувствительные реквизиты есть, сколько заполнено, образец в маске (цифры 9, буквы А/а), расширения, регламентные задания. В отчет реальные значения не попадают |
| `ВЫПОЛНЕНИЕ` | Замена по правилам `1c/rules/<профиль>.txt`, отключение регламентных заданий. Только если путь базы содержит `_test`, указан `ПОДТВЕРЖДЕНИЕ=ТЕСТОВАЯ_КОПИЯ` и база еще не обезличена |
| `ПРОВЕРКА` | По снимку хешей исходных значений: ни одно не должно остаться; верна ли контрольная цифра у всех синтетических ИИН и IBAN; все ли пользователи обезличены |
| `ОДАТА`, `ОДАТАСБРОС`, `КАНАРЕЙКИ`, `УДАЛИТЬКАНАРЕЙКИ` | Для проверки шлюза на живом OData: включить или очистить стандартный интерфейс OData для справочников, посадить канарейки из JSON в базу контрагентов, удалить их |
| `ПОЛЬЗОВАТЕЛИ` | Замена логинов, полных имен и паролей пользователей базы и имен элементов справочника «Пользователи» (кроме оставляемых); `ПРОВЕРКАПОЛЬЗОВАТЕЛЕЙ` - только проверка |
| `ОСТАТКИ` | Поиск по всем строковым реквизитам и табличным частям (не только по правилам) значений, похожих на ИИН/БИН, IBAN KZ, e-mail |
| `СНИМОК` | Только чтение: записывает хеши исходных значений по правилам (запускать на копии базы **до** замены, если снимок потерян) |
| `ЗАЩИТА` | Только для копии (`_test` в пути): выключает у пользователей базы предупреждение об опасных действиях, чтобы платформа не спрашивала разрешения открыть обработку |
| `САМОПРОВЕРКА` | Образцы и массовая проверка генераторов (по 1000 значений ИИН, БИН, IBAN, ИНН 10/12, СНИЛС): длина и контрольные цифры |

Значения заменяются детерминированно (HMAC-SHA256 с секретом запуска): один исходный идентификатор везде превращается в один и тот же
синтетический, ссылки и совпадения между справочниками и документами сохраняются. Замена идет объектами с `ОбменДанными.Загрузка`, порциями
по 500 записей; при ошибке открытые транзакции откатываются.

Результаты на копиях баз (по снимку хешей исходных значений, независимой проверкой в той же обработке):

| Профиль | База | Объем | Результат |
|---|---|---|---|
| KZ | Бухгалтерия для Казахстана 3.0 | 20 тыс. контрагентов, 1 тыс. физлиц, 17 тыс. договоров, документы | 20 групп правил без ошибок; из 6 049 значений идентификаторов и счетов исходных 0; 1 275 IBAN KZ с верным контролем; 8 идентификаторов длиной 11 цифр уже были такими в исходной базе (опечатки), остались той же длины |
| RU | Бухгалтерия предприятия 3.0 | 580 контрагентов, документы, зарплатные ведомости, отчетность (89 групп правил с табличными частями) | исходных значений 0 из 3 055; все 1 811 ИНН с верным контролем; поиск остатков по ИНН/IBAN/e-mail без ПДн (остались коды бюджетной классификации, номера документов, служебные идентификаторы) |

Регистры сведений, подчиненные регистратору, обрабатываются по регистратору; регистры, у которых измерение недоступно в отборе набора, читаются выборкой и пишутся целиком.

### Известные пробелы

- Пользователи: учетные записи информационной базы (логин, полное имя, пароль) и элементы справочника «Пользователи» обезличиваются (режим `ПОЛЬЗОВАТЕЛИ`, он же последний шаг `ВЫПОЛНЕНИЯ`); остаются текущий пользователь, перечисленные в `ОСТАВИТЬ` и служебные записи БСП (`ОтправкаСерверныхОповещений`, `EDIEvents`). Внешние пользователи не обрабатываются.
- Табличные части обрабатываются правилами вида `Вид.Объект.ТабличнаяЧасть`, но правила пишутся вручную по результатам инвентаризации (в инвентаризацию табличные части входят). Для строк без собственного ИНН имя лица берется по документу и номеру строки, поэтому может не совпасть с именем того же лица в справочнике.
- Номера договоров и входящих документов с 12 цифрами остаются; идентификаторы нестандартной длины сохраняют длину, а не получают контрольную цифру.
- Телефоны вне контактной информации режимом `ОСТАТКИ` не ищутся.
- Журнал регистрации обработка не чистит: копия базы делается без журнала. Присоединенные файлы в информационной базе очищаются правилами `очистить_хранилище`, файлы в томах на диске обработка не трогает.
- Номер ПФР/СНИЛС и ИНН в `ХранилищеЗначения` и в вложенных XML не ищутся, только строковые реквизиты.
- Копия базы - это обезличивание «до использования»: после замены обработку повторно запускать нельзя (метка о выполнении).

### Грабли платформы (1С 8.3.27), найденные при разработке

- `Формат(0, "ЧГ=0")` возвращает **пустую строку**, а не `0`. Цифры для идентификаторов берите из строки `"0123456789"`, нули дополняйте через `Прав("000..." + Формат(...), N)`. Из-за этого терялись нули в синтетических номерах, а ИИН с контрольной цифрой 0 и ИНН с последней цифрой 0 получались на знак короче.
- `ПолучитьHMAC` в этой версии недоступен, HMAC-SHA256 собирается вручную на `ХешированиеДанных`.
- `Новый Запрос(...).Выполнить()` и `Новый Файл(...).Существует()` нельзя, нужна промежуточная переменная.
- `Попытка` - ключевое слово, имя переменной цикла так не назвать. `СтрПовторить`, `Выполнить` как имя функции - тоже недоступны.
- При каждом запуске обработки платформа может спросить «Разрешить открывать данный файл?», если у пользователя включена защита от опасных действий. Ключ `/DisableUnsafeActionProtection` этого не всегда достаточно; флаг снимается режимом `ЗАЩИТА` или через COM-коннектор (`InfoBaseUsers`, `UnsafeOperationProtection.UnsafeOperationWarnings = False`, обращаться к членам нужно через `InvokeMember`, PowerShell их напрямую не видит).
- Внешняя обработка в режиме `/Execute` без формы с `ПриОткрытии` молча ничего не делает; `ЗавершитьРаботуСистемы(Ложь, Истина)` перезапускает клиент, нужен один аргумент.
- Ошибка внутри открытой транзакции без `ОтменитьТранзакцию` откатывает при выходе из сеанса **все** последующие записи: при ошибке откатывайте транзакции в цикле `Пока ТранзакцияАктивна()`.
- Регистр, подчиненный регистратору, пишется только набором с отбором по `Регистратор`.
- Измерение регистра сведений нельзя менять внутри набора с отбором по нему: старые записи удаляются, новые пишутся под новым ключом.
- `ПроверитьВалидность` и режим `ОСТАТКИ` должны считать значения неверной длины, а не пропускать их: именно так остались незамеченными укороченные IBAN. Режим `САМОПРОВЕРКА` прогоняет тысячу значений каждого генератора.

## Что проверено, а что нет

- IBAN, ИНН, СНИЛС, ОГРН: проверено по публичным образцам, тесты в `tests/test_checksums.py`.
- ИИН/БИН: алгоритм совпадает с типовой проверкой `БИНИИНСоответствуетТребованиям` (`ОбщегоНазначенияБККлиент`, Бухгалтерия для Казахстана 3.0.73): веса 1..11, модуль 11, при остатке 10 повторный расчет с весами 3..11, 1, 2; если и он дает 10 - номер неверный. СИК: латинские буквы без `O`, как в типовой проверке.
- Сверка с живым валидатором на реальном номере не проводилась: реальных номеров в репозитории нет по замыслу.

## Чего комплект не обещает

- Токены защищают идентификаторы и известные значения. Суммы, даты, номера документов остаются, и по ним можно опознать контрагента.
- Свободный текст без словаря (сокращения, чужие формы названий) может пройти открытым. Поэтому шлюз работает по белому списку полей.
- Это не юридическая консультация: передачу персональных данных за границу регулирует закон, уточняйте у юриста.
